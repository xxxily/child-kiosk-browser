# 首屏应用管理体验优化需求文档

## 背景

当前首屏应用由 `KioskMainScreen` 展示启用状态的 `WebAppEntity`，并按分类 Tab 过滤。应用卡片点击会打开网页，长按在允许编辑时会直接进入编辑流程。这个行为对家长配置来说效率还可以，但不符合“首屏像系统桌面一样管理应用”的心智模型，也容易让长按这个高频入口只能承载单一编辑动作。

本需求将首屏应用管理升级为桌面式交互：

- 应用可以在首屏拖拽排序，并持久保存。
- 长按应用不再直接编辑，而是弹出功能菜单。
- 功能菜单提供编辑、删除、查看详情、调整位置等操作。
- 所有管理动作必须继续遵守 kiosk 安全边界和家长验证策略。

## 现状约束

- 首屏只展示 `isEnabled = true` 的 Web 应用。
- 数据表 `web_apps` 当前没有独立排序字段，DAO 使用 `created_at DESC` 排序。
- 应用分类包括全部、游戏、视频、绘本、学习、工具、其他；分类 Tab 只是过滤当前列表。
- 真实网页打开后仍由 `WebViewActivity -> FrameLayout -> WebView` 承载，本需求不改变网页渲染路径。
- 首屏 Compose UI 必须同时适配竖屏、横屏、手机窄屏、平板和短高度设备。

## 目标

- 首屏应用具备可理解、可恢复、可持久化的手动排序能力。
- 长按首屏应用时展示上下文菜单，避免直接跳转到编辑。
- 管理菜单覆盖常用动作：打开、编辑、删除、查看详情、调整位置、刷新图标。
- 编辑、删除、调整排序等管理动作必须受家长验证或 `allowWebAppEdit` 权限控制。
- 删除和编辑要尊重应用来源，尤其是订阅来源应用不能被误删为本地永久删除。
- 排序、菜单、确认弹窗在横竖屏和小屏下均不裁切，关键操作始终可触达。

## 非目标

- 不实现 Android 系统桌面 Launcher 集成。
- 不支持拖拽到系统桌面、其他应用或 WebView 页面内部。
- 不做跨设备同步排序。
- 不改变 WebView 沙箱、白名单访问策略或网页打开流程。
- 不把真实网页宿主改为 Compose `AndroidView`。

## 用户角色

- 儿童用户：点击应用打开允许访问的网站，不应能绕过验证编辑、删除或重排应用。
- 家长/管理员：通过验证后可以整理首屏、编辑应用信息、删除或隐藏应用、查看应用详情。
- 维护者：需要有明确的数据模型、迁移规则和验收标准，避免排序只停留在临时 UI 状态。

## 功能需求

### 1. 首屏拖拽排序

- 首屏应用支持拖拽调整显示顺序。
- 排序结果必须持久保存到 Room，应用重启、切换分类、横竖屏切换后仍保持一致。
- 排序以首屏全局顺序为主。分类 Tab 只过滤显示，不维护另一套独立排序。
- 在“全部”Tab 中拖拽时，调整所有启用应用的全局显示顺序。
- 在某个分类 Tab 中拖拽时，只调整该分类内可见应用的相对顺序；切回“全部”Tab 后应能看到该分类内顺序已同步变化。
- 拖拽过程中应显示明确的视觉反馈：被拖动项抬起、原位置占位、目标位置变化。
- 列表内容超过屏幕高度时，拖到上下边缘应支持自动滚动。
- 单个应用或空列表时不进入无意义的排序状态。
- 拖拽完成后立即保存；保存失败时回滚 UI 顺序并提示“排序保存失败，请重试”。

### 2. 长按功能菜单

- 长按应用不再直接调用编辑。
- 长按后触发震动反馈，并展示与该应用关联的功能菜单。
- 菜单基础动作：
  - 打开：等同于点击应用。
  - 编辑：进入现有添加/编辑应用对话框。
  - 删除/移除：进入删除确认流程。
  - 查看详情：展示应用详情面板。
  - 调整位置：进入排序状态或提示可直接拖动该应用。
  - 刷新图标：重新抓取或冻结该应用图标。
- 菜单应根据屏幕空间选择呈现方式：
  - 空间充足时可使用应用旁的弹出菜单。
  - 窄屏、短高度或横屏空间不足时使用底部操作面板。
- 菜单、详情面板、删除确认弹窗必须设置安全宽高约束；内容过多时可滚动，确认/取消按钮始终可见。
- 点击菜单外部、返回键或选择动作后应关闭菜单。
- 长按打开菜单后，不应继续触发应用打开。

### 3. 手势冲突处理

长按既要支持菜单，又要支持桌面式拖拽，需要明确分流规则：

- 手指长按达到阈值后，先进入“应用已选中”状态并给出震动反馈。
- 如果手指继续移动并超过拖拽阈值，关闭菜单或不展示菜单，进入拖拽排序。
- 如果长按后未发生有效拖动，松手时展示功能菜单。
- 菜单中的“调整位置”可作为可发现入口，进入排序模式后显示拖拽提示和退出按钮。
- 排序模式下，点击应用不打开网站；点击空白区域或完成按钮退出排序模式。

### 4. 权限与验证

- 当 `allowWebAppEdit = true` 时，长按可直接展示管理菜单。
- 当 `allowWebAppEdit = false` 时，长按不得直接展示可编辑菜单；目标行为是先进入家长验证流程，验证通过后为本次操作临时展示该应用菜单。
- 如果当前策略明确不允许在首屏发起管理验证，则长按只提示“请进入配置后台管理应用”，不执行任何管理动作。
- 验证失败或取消时，不展示菜单，不执行任何管理动作。
- 删除、编辑、调整排序、刷新图标属于管理动作，必须在已授权上下文中执行。
- “打开”是普通使用动作，不要求额外授权。
- 菜单和验证流程不能依赖系统软键盘完成关键输入，应沿用项目中适配 kiosk 的验证控件。

### 5. 删除与移除规则

- 本地添加应用和预设应用：删除前弹确认；确认后可删除对应 `web_apps` 记录。
- 订阅来源应用：不做本地永久删除；菜单文案应使用“从首屏移除”或“禁用”，实际行为为设置 `isEnabled = false`，并提示“订阅网站请在订阅源中管理”。
- 删除或禁用当前首屏应用后，列表应立即更新。
- 如果删除的是当前正在 WebView 中打开的应用，不强制关闭已打开页面；下次回到首屏后不再展示。
- 删除确认文案必须包含应用名称和域名，降低误删风险。

### 6. 查看详情

详情面板展示以下信息：

- 应用名称。
- 完整 URL 和 Host。
- 分类。
- 来源类型：本地、预设、订阅。
- 是否启用。
- 图标来源：内置图标、缓存图标、网络图标。
- 创建时间。
- 当前显示顺序。

详情面板快捷动作：

- 打开应用。
- 编辑应用；订阅来源应用置灰并说明原因。
- 复制链接。
- 删除/移除；订阅来源使用“从首屏移除”。

### 7. 刷新图标

- 对网络图标或可发现图标的应用，允许从菜单触发“刷新图标”。
- 刷新过程应在 IO 线程执行，完成后更新当前应用记录。
- 刷新失败时保留原图标并提示失败原因。
- 对内置图标应用，动作可置灰或显示为“更换图标”，避免无意义刷新。

## 数据模型需求

### 排序字段

在 `WebAppEntity` 中新增持久化排序字段：

- 字段名建议：`display_order`
- 类型：`Long`
- 默认值：`0`
- 语义：数值越小越靠前。

DAO 查询排序应从当前的 `created_at DESC` 改为：

```sql
ORDER BY display_order ASC, created_at DESC, id ASC
```

保留 `created_at` 和 `id` 作为兜底排序，避免旧数据或异常数据顺序不稳定。

### 迁移规则

- 数据库版本从 6 升级到 7。
- 新增 `MIGRATION_6_7`，执行：
  - `ALTER TABLE web_apps ADD COLUMN display_order INTEGER NOT NULL DEFAULT 0`
  - 按旧规则 `created_at DESC, id ASC` 回填递增顺序，确保升级后用户看到的默认顺序与升级前一致。
- 新增应用时，默认追加到当前列表末尾。
- 白名单订阅刷新时：
  - 已存在应用保留原 `display_order`。
  - 新增订阅应用追加到末尾。
  - 禁用或移除的应用不要求重排已有顺序。

### 批量保存

- DAO 需要提供批量更新排序的方法，避免拖拽完成后逐条无事务写入。
- 排序保存应在 `Dispatchers.IO` 中执行。
- UI 层先乐观更新，数据库失败时回滚。

## 交互与视觉要求

- 应用卡片触控区域继续保持适合儿童点击的尺寸，主触控目标尽量不小于 72dp。
- 拖拽状态不能导致标题、分类 Tab、底部内容互相遮挡。
- 横屏短高度下，菜单和详情面板必须可滚动。
- 竖屏窄宽度下，菜单动作应换行或使用底部面板，不得横向裁切中文文本。
- 长应用名在卡片上继续省略显示，详情面板展示完整名称。
- 拖拽排序时应禁用 WebView 预打开和点击打开，避免误触。
- 使用清晰的图标和短文案；危险动作使用红色或破坏性样式并二次确认。

## 状态与边界场景

- 空列表：显示现有空状态，不展示排序入口。
- 仅一个应用：长按仍可展示菜单，但“调整位置”置灰。
- 当前分类无应用：不展示排序入口。
- 切换分类 Tab 时：关闭已打开菜单，退出拖拽中的临时状态。
- 横竖屏切换时：关闭菜单或重新计算菜单锚点；排序结果不能丢失。
- 应用被删除后：如果菜单或详情仍打开，应自动关闭。
- 订阅刷新与手动排序同时发生时：以本地已保存排序为准，新应用追加到末尾。
- 图标刷新、删除、排序均不能阻塞主线程。

## 技术实现建议

- `KioskMainScreen` 增加首屏管理状态：
  - 当前长按选中的应用。
  - 是否处于排序模式。
  - 当前拖拽中的应用 id。
  - 临时排序列表。
- 首屏列表继续使用 Compose，真实网页仍由 `WebViewActivity` 的原生 WebView 路径打开。
- 可优先在现有 `LazyColumn + Row chunk` 结构上实现拖拽排序；若复杂度过高，再评估引入维护活跃、依赖轻量的 Compose reorder 库。
- 不新增 Android 权限。
- 菜单动作复用现有后台编辑对话框和数据库 DAO 能力，避免复制一套应用编辑逻辑。
- 排序字段变更需要同步默认预设应用初始化、白名单订阅导入、历史添加到白名单等所有创建应用入口。

## 实施分期

### 第一阶段：菜单与详情

- 长按首屏应用展示功能菜单。
- 编辑改为从菜单进入。
- 支持删除/移除确认。
- 支持查看详情。
- 保持现有排序规则不变。

### 第二阶段：排序持久化

- 新增 `display_order` 字段和 Room 迁移。
- DAO 按新字段排序。
- 新增应用、订阅导入、历史添加白名单时正确追加顺序。

### 第三阶段：拖拽排序

- 首屏支持拖拽排序和自动滚动。
- 支持分类 Tab 内相对排序。
- 排序保存失败可回滚并提示。

### 第四阶段：增强动作

- 支持刷新图标。
- 支持详情面板中的复制链接、快速打开、来源说明。
- 根据使用反馈补充批量整理或分类移动能力。

## 验收标准

- 长按首屏应用不会直接打开编辑，而是展示功能菜单。
- 菜单中点击“编辑”能进入现有编辑流程。
- 菜单中点击“删除/移除”会先确认，确认后首屏立即更新。
- 订阅来源应用不会被本地永久删除，文案能解释应在订阅源中管理。
- “查看详情”能展示名称、URL、分类、来源、图标来源、创建时间和显示顺序。
- 拖拽调整应用顺序后，重启应用仍保持新顺序。
- 在分类 Tab 内排序后，切回“全部”Tab 能看到该分类内相对顺序已变化。
- 竖屏手机、横屏短高度和平板宽屏下，菜单、详情、确认按钮均不裁切且可触达。
- 未通过家长验证时，儿童用户不能编辑、删除、刷新图标或调整排序。
- Kotlin 编译通过：`:app:compileDebugKotlin`。
