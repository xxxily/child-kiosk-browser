# 网页 App 容器能力增强规划

## 背景

当前项目已经从单纯的儿童安全浏览器，逐步演进为“可信网页 App 的承载容器”。网页 App 负责主要交互、页面渲染和业务逻辑；Android 容器负责补齐普通浏览器或 Android WebView 受限、缺失、不稳定或难以统一管理的能力。

定位能力增强已经证明这条路线可行：对可信 Origin 注入标准化桥接能力，由容器通过系统或高德 SDK 提供更稳定的定位结果，同时保留权限控制、诊断记录和按版本构建。后续能力增强不应继续做成零散开关，而应形成一套可治理、可审计、可扩展的“容器能力平台”。

## 当前基础

已有能力基础：

- `WebViewActivity -> FrameLayout -> WebView` 原生承载路径已经稳定，真实网页不依赖 Compose `AndroidView`。
- `WebViewRuntimeConfig` 已覆盖大量运行时策略：多窗口、文件访问、定位、混合内容、长按、UA、广告过滤、SSL、媒体采集、文件选择、全屏视频、下载、下拉刷新、调试工具、自定义 JS 注入、Scheme 黑名单、站点黑名单和原生定位增强。
- `CapabilityEnhancementsScreen` 已经作为“能力增强”后台入口，目前主要承载网页定位增强。
- `SiteInfoContent` 已经具备当前站点安全状态、定位、原生定位托管、摄像头、麦克风、文件选择和外部 Scheme 的快捷配置雏形。
- 悬浮球面板已经成为网页内的容器级操作入口，可继续扩展页面工具、站点信息、调试、收藏、历史等操作。
- standard/enhanced 双构建已经跑通，后续可以继续把重 SDK 能力放入 enhanced 或独立 flavor。

主要短板：

- 缺少统一的“网页 App 能力契约”：网页无法稳定发现当前容器版本、可用能力、授权状态和调用方式。
- 各能力目前分散在 WebView 配置、站点面板、权限弹窗和后台设置中，缺少统一注册、审计和诊断模型。
- 大多数能力仍是“允许/禁止 WebView 原生行为”，还没有升级为“可信网页 App 可主动调用的容器 API”。
- 缺少面向网页 App 开发者的集成规范、测试页面和兼容性说明。

## 设计原则

1. **白名单优先**：增强能力只对明确可信的 WebApp/Origin 开放，不因网页能运行在容器里就默认获得能力。
2. **最小授权**：每项能力独立开关、独立 Origin 允许列表、独立审计；禁止用一个总开关放开所有能力。
3. **标准优先**：优先增强现有 Web 标准 API，例如 `navigator.geolocation`；无法标准化时再提供 `window.ChildKiosk` 命名空间。
4. **可解释可撤销**：管理员必须能看到能力用途、授权对象、最近调用记录，并能一键撤销。
5. **能力分层构建**：不需要 SDK 的能力进入 standard；依赖高德、扫码、推送、蓝牙、USB 等重能力时进入 enhanced 或后续专用 flavor。
6. **跨进程显式同步**：影响 `:webview` 进程的配置必须通过 Intent 快照、runtime 文件或主进程代理同步，不依赖 WebView 进程读取新鲜 SharedPreferences。
7. **容器兜底但不绑死业务**：网页 App 应能在普通浏览器中降级运行，在 Child Kiosk Browser 中获得增强体验。

## 总体架构规划

### 1. 能力注册表

新增统一能力模型，后台、站点面板、桥接注入、诊断页都从同一注册表读取。

建议字段：

- `capabilityId`：稳定 ID，例如 `location.native`, `files.picker`, `notifications.local`。
- `displayName`：后台展示名。
- `category`：定位、文件、媒体、设备、系统、调试、集成。
- `availability`：standard 可用、enhanced 可用、需要 Android 版本、需要系统权限、需要外部 SDK。
- `defaultPolicy`：默认关闭、默认询问、默认允许白名单。
- `originPolicy`：允许列表、黑名单、按 WebApp 绑定、按分类继承。
- `runtimeApplyMode`：立即生效、新打开网页生效、重启应用生效。
- `auditLevel`：不记录、摘要记录、详细记录。

### 2. 网页侧能力契约

提供只读能力发现 API：

```js
window.ChildKiosk?.getCapabilities()
window.ChildKiosk?.getAppContext()
window.ChildKiosk?.requestCapability("location.native")
```

返回信息应包含：

- 容器版本、standard/enhanced 版本类型。
- 当前 WebApp ID、Origin、是否在白名单中。
- 可用能力列表和授权状态。
- 每项能力的降级建议。

要求：

- `ChildKiosk` 命名空间只能注入到主框架，默认不向 iframe 开放。
- 注入必须在 document-start 尽早完成，避免网页 App 初始化时无法发现能力。
- 所有回调必须带 request id，避免并发请求串线。

### 3. 权限与审计中心

每个能力都要有统一审计记录：

- 时间。
- Origin / WebApp。
- 能力 ID。
- 请求类型。
- 结果：允许、拒绝、系统权限缺失、超时、异常。
- 耗时。
- 简要原因。

后台能力增强页应提供：

- 最近调用记录。
- 按能力筛选。
- 按 Origin/WebApp 筛选。
- 清空记录前二次确认。
- 复制原始诊断信息。

### 4. 站点级能力面板

Site Info Panel 应从“权限快捷配置”升级为“当前网页 App 能力面板”：

- 当前站点安全状态。
- 当前 WebApp 身份。
- 已授权能力。
- 最近能力调用摘要。
- 快捷撤销单项授权。
- 清除此站点数据。
- 当前 Origin 可用的增强能力说明。

## 能力路线图

### P0：平台底座与现有能力收束

P0 目标是把现有零散能力收束成可治理平台，避免后续继续堆功能。

#### P0.1 能力注册与配置模型

需求：

- 建立统一 `CapabilityRegistry`。
- 后台“能力增强”页按能力卡片展示，不再把所有配置直接堆在一个页面。
- 每个能力卡片可进入详情页，详情页包含开关、允许列表、诊断、说明。
- 配置保存必须明确生效范围：立即、新打开网页、重启。

验收：

- 定位增强迁移为注册表中的第一个能力。
- 新增第二个能力时不需要复制整页 UI。
- 后台能显示当前安装版本支持哪些能力，不支持的能力说明原因。

#### P0.2 容器能力发现 API

需求：

- 注入 `window.ChildKiosk` 只读能力发现 API。
- 提供容器版本、构建类型、WebApp/Origin、能力列表。
- 对不在白名单/允许列表的网页返回空能力或只返回安全基础信息。

验收：

- 白名单网页可以读取当前容器能力。
- 非白名单网页不能获得敏感能力信息。
- 网页可根据能力发现结果决定是否启用增强体验。

#### P0.3 统一能力审计

需求：

- 抽象通用 `CapabilityAuditRecord`。
- 定位审计迁移或兼容到统一审计模型。
- 审计详情默认简洁展示，原始诊断折叠。

验收：

- 管理员可以看到某个网页 App 最近调用了哪些增强能力。
- 清空审计需要二次确认。
- 复制诊断保留完整原始信息。

#### P0.4 Site Info Panel 对齐能力模型

需求：

- 站点信息面板展示当前 Origin 已启用的能力。
- 可从面板快速撤销当前站点的定位、媒体、文件、Scheme 等授权。
- 支持从当前站点面板跳转到能力详情页。

验收：

- 管理员不需要进入后台深层页面，也能处理当前网页 App 的能力误用。
- 权限变更能同步当前 Activity 内存配置。

### P1：网页 App 常用体验增强

P1 目标是补齐教育、地图、工具、绘本、小游戏等网页 App 最常遇到的浏览器短板。

#### P1.1 文件选择与安全文件输出

现状：已有 WebView 文件选择询问、站点黑名单和下载能力。

增强方向：

- 为可信网页 App 提供容器文件选择 API，支持图片、视频、音频、文档类型过滤。
- 支持拍照/录音后返回文件 URI 或 Blob URL。
- 下载由容器托管，提供进度、完成、失败状态。
- 支持“保存到应用私有文件区”和“导出到系统下载目录”两种路径。

适用场景：

- 作业上传。
- 头像上传。
- 绘画作品导出。
- 网页生成 PDF/图片后保存。

安全要求：

- 默认不暴露真实文件路径。
- 每次选择必须有用户动作触发。
- 大文件要有大小限制和超时。
- 审计记录文件类型、大小、结果，不记录文件内容。

#### P1.2 媒体采集与扫码

现状：已有摄像头/麦克风权限询问和站点黑名单。

增强方向：

- 提供原生扫码能力：二维码、条形码。
- 提供受控拍照能力：拍一张照片返回给网页，而不是长期开放摄像头流。
- 提供短录音能力：限制最长时长、格式和大小。
- 对需要实时摄像头的网页继续走标准 WebRTC 权限。

适用场景：

- 扫码加入课堂。
- 扫教材码打开内容。
- 拍照提交作业。
- 录音跟读。

安全要求：

- 扫码/拍照/录音必须有明显原生界面。
- 每个能力可按 Origin 单独授权。
- 不提供静默采集。

#### P1.3 本地通知与提醒

普通 Android WebView 对 Web Notifications 支持和后台行为不稳定，容器应提供受控通知能力。

增强方向：

- 网页 App 可请求创建本地提醒。
- 支持一次性提醒、倒计时提醒、每日固定时间提醒。
- 通知点击后回到对应 WebApp/URL。
- 后台可查看和清理某 WebApp 创建的提醒。

适用场景：

- 学习任务提醒。
- 休息提醒。
- 作业截止提醒。
- 番茄钟。

安全要求：

- 默认关闭，按 WebApp 授权。
- 限制单个 WebApp 的提醒数量。
- 不支持未经授权的营销推送。
- 通知内容需审计摘要。

#### P1.4 剪贴板与分享

增强方向：

- 提供受控复制文本、读取剪贴板、分享文本/图片的容器 API。
- 写剪贴板可低风险放宽，读剪贴板必须用户确认。
- 分享通过 Android Sharesheet，但儿童/kiosk 模式下可限制可见目标。

适用场景：

- 复制课程邀请码。
- 分享学习成果给家长。
- 从网页生成图片并分享。

安全要求：

- 读剪贴板必须弹确认。
- 分享目标应受 kiosk 安全策略限制。
- 审计记录文本长度和类型，不记录完整敏感内容。

#### P1.5 WebApp 元数据与运行环境

增强方向：

- 容器向网页提供当前 WebApp 信息：标题、分类、WebApp ID、容器版本、构建类型。
- 提供安全区、横竖屏、悬浮球状态、是否 kiosk 模式等环境信息。
- 提供主题偏好、字体缩放、触控模式等 UI 环境信息。

适用场景：

- 网页根据容器环境优化布局。
- WebApp 根据儿童模式隐藏不适合入口。
- 出问题时网页可上报容器版本。

安全要求：

- 不暴露设备唯一标识。
- 不暴露签名 SHA1、Key 指纹等敏感配置给网页。

#### P1.6 离线与缓存治理

增强方向：

- 为 WebApp 提供“预缓存资源包”或“离线包”管理。
- 支持管理员为某 WebApp 清理数据、重置 Service Worker、查看占用空间。
- 支持按 WebApp 统计 Cookie、LocalStorage、IndexedDB、CacheStorage 使用情况。

适用场景：

- 绘本/课程离线可用。
- 弱网环境下打开更稳定。
- 网站数据异常时一键重置。

安全要求：

- 离线包来源必须绑定白名单/订阅源。
- 不允许网页随意写入无限缓存。
- 提供配额和清理策略。

### P2：进阶设备与系统集成

P2 目标是覆盖少数高价值网页 App 的高级场景，默认不开放。

#### P2.1 原生导航与地图增强

在定位增强基础上继续扩展：

- 当前位置持续跟踪状态可视化。
- 地图 App 可请求打开外部导航，但必须经过 Scheme Broker。
- 支持坐标系转换工具 API。
- 支持地理围栏提醒，但默认关闭。

适用场景：

- 校园地图。
- 户外学习任务。
- 家长确认的路线导航。

#### P2.2 设备传感器

增强方向：

- 加速度计、陀螺仪、方向传感器。
- 环境光或屏幕亮度建议。
- 只在前台页面可见时提供。

适用场景：

- 科学实验小游戏。
- 方向感互动。
- 运动类学习任务。

安全要求：

- 默认关闭。
- 限频。
- 页面不可见或切后台立即停止。

#### P2.3 蓝牙、USB、局域网设备

增强方向：

- 原生扫码/选择后连接特定蓝牙设备。
- USB 设备授权代理。
- 局域网设备发现和连接。

适用场景：

- 教育硬件。
- 打印机。
- 科学传感器。

安全要求：

- 只支持明确设备类型和白名单厂商/服务 UUID。
- 必须有家长确认。
- 需要 enhanced 或专用 flavor。

#### P2.4 打印与 PDF

增强方向：

- 网页请求打印当前页面或指定 HTML/PDF。
- 容器可生成 PDF 并保存。
- 支持家长配置是否允许打印。

适用场景：

- 打印作业。
- 保存证书。
- 生成学习报告。

安全要求：

- 每次打印必须确认。
- 审计记录页面标题、URL 和结果。

#### P2.5 账号与身份辅助

增强方向：

- 受控的家长授权登录辅助。
- WebApp 可请求“当前孩子昵称/头像/年级”等非敏感资料。
- 后续评估 Passkey/Credential Manager，但不作为默认能力。

安全要求：

- 不提供设备唯一 ID。
- 不提供静默自动登录。
- 儿童身份信息必须由家长明确配置。

### P3：实验性或高风险能力

默认不进入短期实现，只保留方向：

- 后台同步任务。
- 常驻 WebSocket 保活。
- 无障碍自动化。
- 屏幕录制。
- 支付能力。
- 任意外部 App 自动跳转。
- 任意本地文件系统访问。

这些能力风险高、监管和家长信任成本大，必须有明确业务场景、单独设计和默认关闭策略。

## 能力开放策略

建议按三层授权：

### 全局层

- 能力是否在当前安装版本可用。
- 家长是否全局启用。
- 是否需要系统权限或 SDK Key。

### WebApp 层

- 某个 WebApp 是否允许使用该能力。
- WebApp 来源：本地、预设、订阅。
- WebApp 分类是否影响默认策略，例如学习类可申请文件上传，游戏类默认不允许通知。

### Origin 层

- 具体 `scheme://host[:port]` 是否允许。
- iframe 默认不继承主框架能力。
- 子域名不自动继承父域名，除非管理员显式选择。

## 网页 API 设计建议

标准 Web API 优先：

- 定位：继续增强 `navigator.geolocation`。
- 文件选择：优先兼容 `<input type="file">` 和 `showOpenFilePicker` 风格的降级封装。
- 媒体：标准 `getUserMedia` 保留，扫码/拍照走容器 API。
- 下载：继续支持 WebView download listener，同时补充容器托管下载 API。

容器命名空间：

```js
window.ChildKiosk = {
  version: "0.3.x",
  build: "standard|enhanced",
  getCapabilities: async () => [],
  request: async (capabilityId, payload) => {},
  on: (eventName, handler) => {},
  off: (eventName, handler) => {}
}
```

调用约束：

- 所有请求必须返回 Promise。
- 所有错误必须有稳定错误码：`PERMISSION_DENIED`、`UNAVAILABLE`、`TIMEOUT`、`INVALID_ARGUMENT`、`CANCELLED`。
- 所有能力调用都必须带 request id。
- 大 payload 不直接走 JS 字符串，优先用 Uri、临时文件或 WebMessage 通道。

## 后台信息架构

建议后台“能力增强”分为：

- 能力总览：显示当前版本支持能力、已启用数量、最近异常。
- 定位增强。
- 文件与媒体。
- 通知与提醒。
- 站点数据与离线。
- 设备集成。
- 开发者与诊断。

每个能力详情页统一结构：

- 开关和版本可用性。
- 使用说明。
- 系统权限状态。
- 允许的 WebApp/Origin。
- 最近调用记录。
- 测试按钮。
- 原始诊断。

## 构建与发布策略

- standard：只包含系统 WebView、Android framework 能力和轻量容器 API。
- enhanced：包含高德定位、扫码、可能的 ML Kit、设备集成等重能力。
- 后续如果蓝牙/USB/推送 SDK 体积或权限成本过高，可继续拆分 flavor，例如 `deviceEnhanced`。
- 关于页和检查更新必须继续按当前安装版本下载对应 APK。
- README 只公开包名、签名和通用能力说明，不公开用户私有 SDK Key。

## 近期实施建议

### 第一阶段：能力平台化

1. 建立 `CapabilityRegistry` 和通用能力模型。
2. 把定位增强迁移到能力详情页。
3. 增加 `window.ChildKiosk.getCapabilities()`。
4. 建立统一能力审计。
5. Site Info Panel 展示当前站点能力。

### 第二阶段：文件/媒体/下载增强

1. 把文件选择、摄像头、麦克风、下载从“WebView 事件处理”整理成能力模块。
2. 增加扫码、拍照、短录音容器 API。
3. 下载增加进度和结果回调。
4. 能力详情页增加测试入口和最近调用记录。

### 第三阶段：通知、离线与 WebApp 运行环境

1. 提供本地通知/提醒能力。
2. 提供 WebApp 环境信息 API。
3. 提供按 WebApp 的存储占用、清理和离线包管理。
4. 输出网页 App 集成指南和测试页面。

### 第四阶段：高级设备集成

1. 评估蓝牙/USB/打印/PDF 的实际业务需求。
2. 对每项高风险能力单独设计权限、审计和 flavor 策略。
3. 只为明确白名单 WebApp 开放。

## 验收标准

平台级验收：

- 后台能看到所有能力的可用性、开关、授权对象和最近调用。
- 白名单网页能发现能力，非白名单网页不能发现敏感能力。
- 每个能力都能被单独启用、停用、授权、撤销。
- 每个敏感能力调用都有审计记录。
- `:webview` 进程配置变更不会依赖 SharedPreferences 新鲜读取。
- 新增能力不扩大 `AdminConsoleScreen.kt` 或 `CapabilityEnhancementsScreen.kt` 为巨石文件。

网页 App 验收：

- 网页 App 可以通过能力发现 API 做渐进增强。
- 普通浏览器中网页 App 仍可降级运行。
- Child Kiosk Browser 中启用能力后，网页 App 可获得稳定、可诊断的增强体验。

安全验收：

- iframe 默认无法调用敏感能力。
- 未授权 Origin 调用能力时返回稳定错误码。
- 撤销授权后当前页面后续请求立即失败或按文档说明在新开页面生效。
- 审计记录不包含原始坐标、完整文件内容、剪贴板明文等敏感数据。

## 关键风险

- 能力过多导致后台复杂：必须坚持“总览 + 详情页”结构，避免所有配置堆在同一页。
- JS bridge 扩大攻击面：必须只对白名单主框架注入，所有请求都校验 Origin。
- SDK 体积和权限膨胀：通过 flavor 控制，standard 保持轻量。
- WebApp 依赖容器过重：必须提供降级约定和能力发现 API。
- 诊断泄露隐私：审计默认脱敏，原始诊断也不能包含私密内容。

## 结论

后续能力增强的重点不是“再加几个开关”，而是把 Child Kiosk Browser 建成一个受控、可审计、可扩展的网页 App 容器。短期优先完成能力注册、能力发现、统一审计和 Site Info Panel 对齐；随后补齐文件/媒体/下载、通知、离线和 WebApp 环境信息。这样可信白名单网页既能保持 Web 技术栈的开发效率，又能获得普通浏览器难以稳定提供的原生能力托底。
